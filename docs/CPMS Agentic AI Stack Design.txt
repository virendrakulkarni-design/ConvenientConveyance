  This document defines the complete agentic AI architecture for the CPMS platform. It is intended as a technical handover to the solution architect responsible for detailed system design, infrastructure planning, and implementation sequencing.
1. Executive Overview
The Conveyancing Practice Management System (CPMS) is a purpose-built web application for small to medium conveyancing firms operating in South Australia, with a design intent to extend to other Australian jurisdictions. The system replaces fragmented tool stacks with a unified, AI-augmented platform covering the full matter life cycle — from initial client enquiry through to post-settlement record retention.
The AI layer is not peripheral to this system. It is load-bearing. Conveyancing involves high-volume, rule-governed document processing, strict compliance obligations under AUSTRAC AML/CTF, time-sensitive task sequencing, and significant manual overhead in form preparation and external platform coordination. An agentic AI stack that operates with human-in-the-loop (HITL) controls addresses each of these areas directly.

2. Agentic AI Architecture — Overview
The CPMS AI architecture is structured as a multi-agent system with a central orchestrator, specialised sub-agents, a shared context and memory layer, and a human-in-the-loop gateway. The architecture follows a planner-executor pattern: a Supervisor Agent decomposes user intent and routes to domain-specific agents, which execute discrete tasks and return structured outputs for human review before any state-changing action is committed.

2.2 Core Design Principles
Agents propose; humans approve — no external API call or document commit executes without HITL confirmation unless explicitly pre-authorised by firm administrators
Tool calls are idempotent — every external platform operation (PEXA workspace creation, search order, email send) is wrapped in an idempotency layer to prevent duplicate actions on retry
Context is matter-scoped — all agent context is bounded to the active matter; cross-matter data access requires explicit permission
Compliance rules are deterministic — AML/CTF, VOI, and retention checks run on a rule engine, not on LLM inference; the LLM assists with preparation, not policy decisions
Failure is visible — agent errors surface to the HITL panel, never silently swallowed

4. LLM Selection and Usage Strategy
Three Claude model tiers are used across the agent catalogue. Model assignment follows a cost-quality optimisation — heavyweight reasoning tasks use Opus, standard task execution uses Sonnet, and high-throughput classification and API orchestration uses Haiku.
Model
Assigned Agents
Rationale

Supervisor Agent, Legal Advisory Agent

claude-sonnet-4

Balanced quality and throughput for core operational tasks; vision capability for scanned documents
claude-haiku-4

4.1 Context Window Management
Matter context can be large — title searches, contracts, Form 1s, and correspondence accumulate across a matter's life. The following strategies apply:
Active context: Only the current task-relevant subset of matter data is loaded into the agent context window, assembled by a context builder service
RAG for historical and reference data: Legislation, precedents, and master data accessed via retrieval, not loaded wholesale
Summarisation: Long documents are pre-summarised by Haiku before being passed to Sonnet or Opus for action
Session state: Redis-backed short-term session state persists within a matter session; PostgreSQL-backed long-term state persists across sessions
4.2 Prompt Management
All agent system prompts are versioned and stored in the prompt registry
Prompt changes go through a staging environment before production deployment
Firm-specific prompt overrides are permitted for tone and terminology, within guardrails

5.1 Web Automation Approach
For platforms with no public API (SA Water EPIC, RevenueSA, council portals, FRCGW), a browser automation layer using Playwright is used. The automation is deterministic (not LLM-driven) — pre-scripted workflows execute under agent instruction. The LLM determines when and why to trigger the workflow; the automation script executes it.
  Browser automation scripts for government portals must be monitored actively — portal UI changes will break automations. A smoke-test suite should run daily against each portal.
5.2 Email Intelligence Pipeline
Inbound email is a primary data channel for conveyancing operations. The email pipeline processes all firm email through the following stages:
Classification: Haiku model classifies each email as task-actionable, document delivery, FYI, or noise
Entity extraction: Sender, matter reference, document type, and urgency extracted from classified emails
Routing: Task-actionable emails create items in the matter task queue; document deliveries trigger auto-save and classification
Draft response: Client Engagement Agent drafts replies for task-actionable emails; surfaced in HITL panel

6.1 Matter Data Model — Key Entities
Matter — core entity; carries type, stage, property references, client references, key dates, compliance status flags
Client — individual or non-individual entity with sub-types (company, trust, superfund, etc.); linked to VOI records
Property — identified by CT/CR/CL volume/folio, lot, plan type, council assessment number, valuation number
Document — all files attached to a matter; typed, versioned, with source (uploaded, generated, received)

ComplianceRecord — KYC/VOI status, AML/CTF check results, AUSTRAC reporting references
AuditEntry — agent action, HITL decision, user action; matter-scoped; append-only
6.2 Record Retention
Post-settlement, the system generates a comprehensive settlement archive PDF containing: signed authority documents, VOI records, transaction details, adjustment statements, and the settlement ledger. This archive is stored in object storage with a minimum 7-year immutability policy. Interim records with defined validity windows (VOI: 2 years; FRCGW certificates: until expiry) are flagged by the retention scheduler agent before expiry.
7. Human-in-the-Loop Control Design
The HITL system is the primary safety control for the agentic layer. It is not an afterthought — it is a first-class UI component and a mandatory gate on all state-changing operations. The design principle is: the AI does the work, the human owns the decision.
7.1 HITL Gate Classifications
Gate Class
Trigger Condition
UI Behaviour
Hard gate
External API write, financial line change, document dispatch for signature, SMR submission
Execution blocked until explicit user approval; action cannot be pre-authorised
Soft gate
Outbound email draft, matter data population from parsed document, task status change
Shown in review panel with accept/edit/reject; can be bulk-approved by admin setting
Advisory
Legal advisory output, compliance status explanation, suggested action
Surfaced as information only; no execution is pending
Automated (no gate)
Search result file-and-save, appointment confirmation email, payment link generation
Executes automatically; logged in audit trail; reversible within defined window
7.2 HITL Review Panel — UX Requirements
Pending actions queue: displays all pending agent proposals grouped by matter, sorted by urgency
Diff view: for document population and data extraction, shows proposed changes against current state
Context panel: shows the agent's reasoning and the source data that led to the proposal
Approve / Edit / Reject: three options on every hard and soft gate; edits return to the agent for re-generation
Bulk approval: firm administrators can pre-approve specific action classes (e.g. appointment confirmation emails) to reduce queue volume
Audit trail: every approval, rejection, or edit is logged against the user ID and timestamp

8.1 AI Services Deployment Pattern
The AI agent services are deployed as a separate FastAPI microservice cluster alongside the NestJS core backend. Communication between NestJS and AI services is via internal REST/gRPC. This separation allows independent scaling of AI workloads, isolated dependency management for the Python AI ecosystem, and independent deployment of LangGraph agent updates without core application releases.

9.1 RBAC Model
Role-based access control governs both system features and agent capabilities. Minimum required roles:
Principal Conveyancer — full access including HITL approval on all gate classes
Conveyancing Assistant — access to task management, document preparation, HITL approval on soft gates only
Administrator — system configuration, template management, firm settings, user management
Client (external) — access to onboarding portal, document signing portal, and appointment booking only; no internal system access
