SDD-00: SDD Standard, Decision Register & Build Index
Audience: every developer and every AI coding agent working on CPMS Status: Draft v0.1. Decisions marked DEFAULT are binding until changed by an ADR. Decisions marked GIVEN come from the original requirements. Purpose: define exactly how a Software Design Document (SDD) is written and used, so an implementer who has only the SDDs and the repository can build and test a feature without guessing anything.
1. The promise of an SDD
An SDD is complete when an implementer, human or AI, who has read only (a) this document, (b) the SDD for the feature, (c) the SDDs it lists as dependencies, and (d) the repository, can:
write all the code, SQL, configuration and tests for the feature;
name every file, table, column, route, event, error code and permission identically to every other implementer;
prove the feature is finished by running the tests the SDD lists.
If any of the three fails, the SDD has a defect. The defect is fixed in the SDD, never worked around in code.
2. Rules for implementers (humans and AI agents)
#
Rule
R1
The SDD is the only source of truth. Do not infer behaviour from similar systems, common practice, or your training data.
R2
If the SDD does not say something you need, stop that task. Create docs/open-questions/OQ-<number>.md (format in section 10), continue only with tasks that do not depend on the answer, and do not guess.
R3
Do not add fields, endpoints, events, screens, dependencies or behaviour that the SDD does not list. Extra work is a defect.
R4
Use names exactly as written (table, column, route, error code, permission code, event name, config key, file path). Never rename for style.
R5
Write the tests listed in the SDD. Every listed test case ID must exist as a test whose name starts with that ID. Do not delete or weaken a test to make it pass.
R6
Never edit an SDD while implementing. Propose a change with docs/change-requests/CR-<number>.md.
R7
Respect module boundaries. Import only from another module's public api/index.ts.
R8
No TODO, FIXME, HACK comments unless they cite an open question ID, for example // TODO(OQ-014).
R9
Add dependencies only from the approved list in the relevant SDD. A new dependency needs an ADR.
R10
Never put secrets, real client data, or real identity documents in code, tests, logs or fixtures.
R11
Every behaviour that the SDD marks MUST has at least one automated test.
R12
End every task with an Implementation Report (format in section 11).
Keywords MUST, MUST NOT, MAY carry their RFC 2119 meaning. The words should, could, ideally never appear in normative text.
3. Precision standard: what every SDD must specify
This table is the checklist an author uses. A row with no content for a feature is written as Not applicable: <reason>, never left blank.
Subject
Must specify
Database table
Table name; every column with SQL type, nullability, default, constraints, index membership, PII class (none, personal, sensitive, secret), and a one-line meaning; primary key; foreign keys with ON DELETE behaviour; unique constraints; check constraints; RLS policy; triggers; grants per database role; migration file name
API endpoint
HTTP method; full path; authentication requirement; permission code; request headers, path params, query params, body with every field (type, required, min, max, pattern, default); validation rules in order; success status and response body schema; every error status with its error code and the condition that raises it; idempotency behaviour; rate limit; audit event written; one complete request and response example
Use case or command
Input; preconditions; numbered steps; postconditions; transaction boundary; events emitted; behaviour under concurrent execution; behaviour on partial failure
State machine
Every state; every allowed transition with trigger, guard, side effects and event; the error code raised for every other transition
Domain event
Name; version; producer; payload fields with types; consumers; whether consumers must be idempotent
Permission
Code; meaning; roles that hold it by default
Configuration key
Key; type; default; allowed range; scope (platform, tenant, firm, matter); who may change it; effect of changing it
Error code
Code; HTTP status; message template; condition; retryable yes or no
Background job
Name; queue; trigger; concurrency; retry schedule; idempotency key; timeout; what happens after final failure
UI screen
Route; purpose; layout regions; each component; each field with label text, validation and error message text; every state (loading, empty, error, populated, saving); every action with its result; permission needed; keyboard behaviour; accessibility requirements; exact user-visible copy
Test case
ID; type (unit, integration, e2e, security, performance); Given; When; Then with exact expected values
Non-functional
Measurable target and how it is measured
4. Banned vocabulary in specifications
These words signal missing detail. Authors replace them with specific values or rules. Reviewers reject an SDD containing them in normative text.
etc., and so on, appropriate, suitable, reasonable, as needed, if necessary, where applicable, similar to, standard, typical, usually, fast, secure (without a named control), robust, flexible, simple, properly, handle errors (list each error), TBD, to be decided, various, some, relevant.
5. SDD document template
Every SDD uses exactly these sections, in this order. File name: docs/sdd/SDD-<two digit number>-<kebab-name>.md. Requirement statements carry IDs of the form SDD-<nn>-FR-<three digits> (functional) or SDD-<nn>-NFR-<three digits> (non-functional).
Header: number, title, version, status (Draft, Spec-Ready, Implemented), owner, last changed date
Scope: what is built; Out of scope: what is explicitly not built here
Traceability: original requirement IDs (section 7) this SDD satisfies
Dependencies: SDDs and decisions that must be implemented or confirmed first
Glossary: terms used, with Vol 2 definitions linked
Data design: tables (section 3 format), migrations
Domain rules and state machines
Application behaviour: use cases in section 3 format
API specification
Events and jobs
Permissions and configuration
Error catalogue
UI specification (if any)
Security and privacy requirements
Observability: log events, metrics, alerts
Test specification: all test cases
Acceptance criteria: the exact list that makes the SDD Implemented
Open questions: each with an ID, owner, and what is blocked
Change log

9. Spec-Ready checklist
An SDD moves from Draft to Spec-Ready only when a reviewer other than the author ticks every line.
☐ Every section in the template exists, or says Not applicable: <reason>
☐ No banned word (section 4) appears in normative text
☐ Every table has every column typed, with nullability and default
☐ Every endpoint lists every error status with its error code
☐ Every state has a transition list, and every other transition names an error code
☐ Every event, permission, configuration key and error code is declared once and referenced by name elsewhere
☐ Every MUST has a test case ID next to it
☐ Every test case has exact input and exact expected output
☐ Every dependency decision is GIVEN or DEFAULT, or the SDD says what it does if the answer changes
☐ Every user-visible string is written out
☐ Open questions are listed, and none blocks the acceptance criteria
☐ A reader outside the author team has traced one requirement end to end and found no gap
10. Open question protocol
File docs/open-questions/OQ-<three digit number>.md with these fields: SDD and section, question (one sentence), what I need decided (list of concrete options), what is blocked, what I did instead (must be: nothing on the blocked part), raised by, date. The owner answers by editing the SDD, then deleting the file in the same commit.
11. Task card and Implementation Report
Every AI task starts from a task card with these fields:
Field
Content
Task ID
T-<SDD number>-<three digits>
Spec references
Exact requirement IDs, for example SDD-01-FR-004 to SDD-01-FR-009
Files to create or change
Full paths
Must not touch
Full paths or modules
Tests that must pass
Test case IDs
Commands to verify
Exact commands
Every task ends with an Implementation Report containing: requirement IDs implemented; files created and changed; test case IDs run and their results; open questions raised; and the statement Deviations from SDD: none (or the change request IDs).
