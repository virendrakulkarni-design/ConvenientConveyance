1. The product in one page
What: a web-based Conveyancing Practice Management System (CPMS) for small and medium Australian conveyancing firms, starting with South Australia.
Who uses it: non-technical conveyancers, assistants, and accountants (staff), and clients (via a separate portal).
Five products under one roof
Practice core: matters, parties, properties, documents, tasks
Client portal: onboarding, forms, e-sign, VOI/KYC, payment, appointment booking
Integration hub: PEXA, SAILIS, SA Water EPIC, RevenueSA, councils, e-sign, VOI providers
Compliance and trust accounting: AML/CTF, retention, ledgers, statements
AI layer: document extraction, email triage, task agent, legal decision support
Non-goals (v1)
Conveyancing of Business (explicitly out of scope in the requirements)
Building our own payroll engine, VOI identity verification engine, or e-signature legal framework (integrate)
Client-facing AI legal advice (AI supports the licensed conveyancer only)
Any state other than SA (but the design must not block them, see section 9)

3. Ten engineering principles (the non-negotiables)
Modular monolith first. One deployable backend, strict internal module boundaries. Extract a service only with an ADR proving the need.
Domain first, framework second. Business rules live in plain TypeScript domain code, not in controllers or UI components.
Every integration sits behind an adapter. No module calls PEXA, SAILIS or any third party directly. Ever.
Humans approve consequential actions. Automation proposes; people commit. See section 10.
Legally relevant data is append-only. Signed forms, ledger entries, VOI evidence, and template versions are never edited. Corrections are new records that reference the old one.
Configuration over code, within limits. Templates, checklists, fees and stages are data. Business logic is code.
Tenant isolation is enforced by the platform, not by developer discipline. Developers cannot forget a tenant filter.
Everything observable. Structured logs, metrics, traces, audit events from day one.
Buy the regulated, build the differentiating. Integrate VOI, e-sign, payments and payroll. Build workflow, forms engine, and the AI-assisted experience.
Boring technology, clear conventions. Consistency across the codebase beats local cleverness.

5.1 Dependency rules (enforced in CI)
A module talks to another only through its public API (an exported service interface). Never import another module's entities, repositories, or internal files.
No circular dependencies. If A needs B and B needs A, introduce a domain event.
Cross-module reactions use domain events (e.g. MatterSettled triggers retention snapshot and notifications).
audit and tenancy are leaf modules. Everyone may call them; they call nobody.
Enforce with lint rules (e.g. Nx module boundaries or dependency-cruiser) so violations fail the build.
5.2 Anatomy of a module
src/modules/matters/ api/ # public interface other modules may import (index.ts only) domain/ # entities, value objects, domain services, events (no framework imports) application/ # use cases / command + query handlers infrastructure/ # repositories, mappers, adapters http/ # controllers, DTOs, validators matters.module.ts README.md # purpose, public API, events emitted/consumed, owner
Every module has a README.md stating its purpose, public API, events, and owner. A module without one fails review.
6. Multi-tenancy [PROPOSED]
Model: shared database, shared schema, tenant_id on every business table, enforced by PostgreSQL row-level security. The request sets the tenant in the DB session; the database refuses cross-tenant reads.
Why not DB-per-tenant: operational cost for a small team. We keep the option open by never hard-coding assumptions about a shared database (no cross-tenant joins in application code).
Hierarchy: Tenant (organisation) -> Firm (branch/entity) -> User. A tenant may have several firms.
Files: object keys prefixed by tenant_id; access via short-lived signed URLs.
Credentials: third-party credentials are stored per tenant in a secrets vault, never in the application database in plain text.
Tests: an automated cross-tenant leak test suite runs in CI against every endpoint.
Large-customer escape hatch: the schema allows moving a tenant to a dedicated database later.
[DECISION NEEDED] Confirm multi-tenant SaaS versus single-tenant per firm. This section assumes multi-tenant.

Rules
All configuration is versioned. A matter pins the version it started with so a later edit never rewrites history.
Config changes are audited, previewable, and reversible.
Configuration is validated by JSON Schema before it is saved.
Typed core fields plus a configurable extension: matter metadata uses typed columns for fields we compute on (settlement date, price, deposit) and a validated JSON custom_fields for firm-specific extras. Do not create 60 hard-coded columns.
8. Extensibility patterns
8.1 Integration adapter contract
Every external system implements a common port:
interface IntegrationAdapter<TConfig> { id: string; // 'pexa', 'sailis', 'stripe' capabilities(): Capability[]; // what it can do (order search, create workspace) healthCheck(tenant: TenantContext): Promise<Health>; execute(cmd: AdapterCommand, ctx: TenantContext): Promise<AdapterResult>;}
Every adapter must provide: per-tenant credentials, timeouts, retries with backoff, rate limiting, circuit breaker, idempotency keys, request/response logging with secrets redacted, a contract-test suite against recorded fixtures, and a fallback mode (manual task for staff) when the integration is unavailable.
Integrations are classified in Vol 4 as: API (official), Aggregator, Email-based, Portal automation (last resort, flagged fragile), or Manual. The product must remain usable at the Manual level for every integration.

8.3 Domain events
Modules publish events (MatterCreated, FormSigned, SearchReceived, SettlementCompleted). Subscribers react. Events are versioned, persisted via a transactional outbox, and handled idempotently.
9. The Proposed Action pattern (human-in-the-loop)
All automation, whether AI, email rule or scheduled job, follows one pipeline:
Trigger -> Propose -> Review -> Commit -> Audit
Propose: the automation creates a Proposal record containing the intended action, its parameters, the evidence (source email, document excerpt, extracted field with confidence), and the actor (which rule or model).
Review: a human approves, edits, or rejects. Low-confidence and high-risk actions always require review.
Commit: only the system executes the approved action, through the normal domain API. Automation never writes to domain tables directly.
Audit: the proposal, reviewer, edits, and result are stored immutably.

This single pattern covers the chat assistant, email-to-task, document ingestion, and PEXA actions.
10. Data and correctness rules
Immutability: signed forms, ledger journal entries, VOI evidence, audit events, and published template versions are append-only. Enforce with database permissions and triggers, not just application code.
Snapshots: when a form is sent, store a snapshot of the bound data. Later changes to the matter never alter what the client signed.
Money: store as integer cents plus currency. Never floating point. Ledger is double-entry. Corrections are reversal entries. Reconciliation is automated and reported.
Time: store UTC, display in Australia/Adelaide (or the firm's configured zone). Dates without time (settlement date) are stored as dates, not timestamps.
IDs: UUIDv7 (sortable) for primary keys. Human-readable matter references are separate and configurable per firm.
Soft deletion: business data is archived, not deleted. Hard deletion happens only through the retention process with a logged reason.
Migrations: forward-only, reviewed, backwards-compatible within one release (expand, migrate, contract).
PII: ID images and sensitive fields use field-level encryption. Raw ID images are retained only as long as the compliance policy requires.
11. API conventions
REST, JSON, OpenAPI generated from code and published. The Angular clients use generated typed clients so contracts cannot drift.
URL style: /api/v1/matters/{matterId}/parties. Nouns, plural, kebab-case.
Versioning: URL major version. Additive changes only within a version.
Errors: one format for all, with a stable machine code and a human message.
{ "error": { "code": "MATTER_STAGE_INVALID", "message": "Cannot move to 'Contracted' without a contract date.", "details": [], "traceId": "..." } }
Pagination: cursor based. Filtering and sorting: documented query parameters.
Idempotency: every create that triggers a side effect accepts an Idempotency-Key header.
Validation: DTOs validated at the boundary; domain invariants validated in the domain.
AuthZ: permission checks declared per endpoint (@RequirePermission('matter.update')), tested.
12. Frontend architecture (summary; detail in Vol 9)
Structure: feature-based folders (features/matters, features/forms), each lazy-loaded. Shared UI in a ui library; shared logic in core.
State: Angular Signals for local and feature state; a small store pattern per feature; server state through a data-access layer with caching. No global state dumping ground.
Components: standalone, OnPush, presentational vs container separation.
Forms: schema-driven renderer for dynamic forms (same renderer in staff app and portal, so what firm designs is what clients see).
Design system: tokens (colour, spacing, type) in one place; Tailwind configured from tokens; Zard UI wrapped, not scattered, so we can swap or restyle it centrally.
Permissions in UI: driven by the same permission names as the API. Hiding a button is never security; the API enforces.
Testing: component tests, plus Playwright end-to-end for the top 20 journeys.
UX principles for non-technical staff
The matter is the home. Everything for a matter is reachable within two clicks from the matter page.
Show the next action. Every matter displays its stage, what is blocking it, and what to do next.
Checklists over menus. The life cycle steps are the navigation spine.
Plain language. Use the words conveyancers use. No developer jargon in the UI.
Safe by design. Confirm irreversible actions, support undo where possible, show what AI changed and why.
Explain automation. Every automated change shows its source and evidence.
Fast data entry. Keyboard friendly, sensible defaults, auto-fill from parsed documents.
Same experience everywhere. One component library, one pattern per task.
Client portal is mobile-first. Clients complete ID capture and signing on phones.
13. Operability
Environments: local, dev, staging (production-like, anonymised data), production.
Infrastructure as code (Terraform) and containerised deploys. No manual changes in production.
CI/CD: every pull request runs lint, type check, unit, integration, contract, and tenant-leak tests; builds are immutable and promoted across environments; production deploys are automated with one-click rollback.
Observability (OpenTelemetry): structured JSON logs with traceId, tenantId, userId; metrics (RED: rate, errors, duration); distributed traces; dashboards per module; alerts tied to runbooks.
Business-level monitoring: integration health, queue depth, failed proposals, overdue reminders, reconciliation mismatches.
Backups: automated, encrypted, cross-region within Australia, with quarterly restore drills.
Feature flags for safe rollout; every risky feature ships dark first.
Runbooks for every alert: what it means, how to check, how to fix, who to call.
Support tooling: a tenant-safe admin console with audited impersonation (read-only by default).
14. Security baseline (summary; detail in Vol 11)
MFA for staff, SSO option (Microsoft/Google), short-lived tokens, secure cookies.
RBAC with fine-grained permissions plus attribute rules (e.g. only the assigned conveyancer or admin may see trust ledger).
Encryption in transit and at rest; field-level encryption for ID data; keys in a managed KMS.
Client portal links are single-purpose, expiring, rate limited, and bound to a matter.
Dependency scanning, secret scanning, SAST, container scanning in CI.
Penetration test before the first pilot; annual thereafter.
Privacy Act (APPs) and Notifiable Data Breaches process documented and rehearsed.
Build habits now that make ISO 27001 and SOC 2 achievable later: change control, access reviews, logging, vendor register.
