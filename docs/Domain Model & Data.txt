A non-individual Party cannot sign. It requires at least one active authorised_signatory relation (or director/trustee relation that the template accepts) to a signing individual.
A trust is modelled as a Party whose trustees are related Parties. The trust deed is a Document linked to the Party.
Identity data that has been verified is not edited. A change creates a new version and flags VOI for re-check if name or residency changed.

5.9 Tasks and checklists (module: tasks; detail in Vol 5)
Two concepts, kept distinct:
Checklist item: a defined step in a matter's life cycle (for example, Order council searches). It comes from a checklist template and has a status (not_started, in_progress, blocked, done, not_applicable). It marks progress through the matter.
Task: assignable work with an owner and due date. A checklist item may spawn tasks. Tasks can also come from email or a user.

Every entity with a status has one state machine, defined as data in code (allowed transitions, guards, side effects). Direct status updates through SQL or generic update endpoints are forbidden.

7.2 Naming and types
Tables: plural snake_case (matter_parties). Columns: snake_case. Foreign keys: <entity>_id. Enums: lowercase snake values.
Money: bigint cents plus currency char(3). Never float, never numeric without scale agreement.
Dates without time-of-day (settlement date): date. Instants: timestamptz in UTC.
Enumerations: reference tables or check constraints, not native DB enums, so adding a value needs no table lock. Values are also defined in code.
JSONB only for: configuration documents, extension fields, extraction output, evidence snapshots. Anything filtered or joined on regularly becomes a column.
Every foreign key has an index. Every tenant-scoped query path starts with tenant_id in the index.
7.3 Row-level security
Every tenant table has a policy tenant_id = current_setting('app.tenant_id')::uuid. The application database role cannot bypass RLS. A migration test fails the build if a table with tenant_id has no policy.
7.4 Constraints the database enforces (not only the app)
Matter has at least one Client party and one Property (deferred constraint checked at stage change from enquiry).
JournalEntry debits equal credits.
Title unique on (tenant_id, register_type, volume, folio) where active.
Published template version cannot be updated.
A signed FormInstance cannot be updated.
Settlement date cannot precede contract date.
A Party of kind entity has an EntityDetail; of kind individual has an IndividualDetail.
7.5 Migrations and seed data
Forward-only, reviewed by one other dev, tested against a production-size snapshot.
Use expand, migrate, contract for any breaking change.
Seed data (system roles, SA councils, default statement items, templates) lives in versioned seed files, loaded idempotently, never hand-edited in the database.

9. Provenance and data quality
Data in a conveyancing file comes from many sources, and staff must know how far to trust each value.
Every parsed or imported value carries a provenance record:
Field
Meaning
source_type
manual, contract_parse, title_search, council_search, api_pexa, client_form, email
source_document_version_id
Which file it came from
confidence
0 to 1 for machine-extracted values
verified_by, verified_at
Human who confirmed it
status
unverified, verified, conflict
Conflict handling: when two sources disagree (for example, the contract address and the title address), the system keeps both, marks the field conflict, and creates a checklist item for staff to resolve. It never silently overwrites.
Implementation: a generic field_provenance table keyed by (entity_type, entity_id, field_path), so adding provenance to a new field needs no schema change.

11. Business invariants (testable rules)
These become automated tests (Vol 12). Each has an ID.
ID
Invariant
INV-01
Every Matter has at least one MatterProperty and at least one MatterParty with a client role
INV-02
A signing recipient for an entity must be a related individual with an active authorised relation
INV-03
A purchaser matter with two or more incoming proprietors requires the joint tenancy or tenants-in-common declaration form
INV-04
If tenancy is true and a property manager is recorded, the authority forms include the continue-with-property-manager question
INV-05
Journal entries always balance; reversals reference an existing entry
INV-06
No ledger entry can be posted to a matter that is closed or cancelled
INV-07
A published template version and a signed form never change
INV-08
A VOI cannot be reused if expired, if name or residency changed, or if the passport fails the validity rule
INV-09
Only accepted extraction results can write to matter data
INV-10
High-risk proposals (money, lodgement, signing) are never auto-committed
INV-11
Cross-tenant reads return zero rows for every table
INV-12
Actual settlement date cannot be set before contract date
INV-13
A matter cannot enter Settlement stage with an unbalanced ledger or missing mandatory authority forms
INV-14
Deleting or archiving a Party with active matters is blocked
